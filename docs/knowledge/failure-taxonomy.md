# Failure taxonomy с реальными примерами

Классификация неуспешных исходов из Приложения C плана, дополненная **фактами
исследования**. Каждая категория снабжена случаем, который действительно
произошёл, — чтобы новый участник узнавал класс по симптому, а не по
определению.

Правило: для любого неуспешного run выбирается одна основная категория и при
необходимости одна вторичная. **Prompt не правится до классификации причины** —
иначе исчезает сам предмет измерения.

| Категория | Значение | Что случилось в исследовании |
| --- | --- | --- |
| `product` | Дефект приложения или backend | **S2, Speecher.** После смены языка на английский весь контент локализован, но подписи вкладок остались русскими. API-проверка прошла, UI-проверка `notContainsText «Настройки»` — нет. Verdict `FAIL`, причина — приложение. **S3, Speecher.** Выбор иконки не сохраняется: `defaultsChanged` показал, что в `UserDefaults` не появилось ничего |
| `test-data` | Ошибка seed, Workspace или teardown | Не встречалась ни разу за 41 прогон: изолированный контекст на run (свежий UUID / контейнер / отдельная комната) снял класс целиком. Неочищенных fixtures — 0 |
| `environment` | Сбой Simulator, Emulator, Metro, API или сети | **Прерванный run этапа 12.** Машина ушла в сон посреди сценария; run остался `started` и был закрыт через `abort` как `BLOCKED`/`environment`, а не удалён. **Этап 7.9:** blobs `netlify dev --offline` молча перестали персистить (POST 201, GET total=0) после резкой остановки — лечилось чистым рестартом |
| `agent` | Ошибка рассуждения или выбора действия | **Этап 7, Android:** `button back` вне модалки выводил приложение на домашний экран и валил следующие шаги — ошибка выбора действия, а не инструмента. **Этап 12, S3:** тап по «Тёмная иконка» вместо «Темная» — ошибка ожидания, а не разметки |
| `sim-use` | Ошибка CLI, daemon, bridge или resolution | **TOOL-LOCALE-001.** Daemon, поднятый в shell без `LANG`/`LC_ALL`, портит кириллицу при `paste`: 67-символьное описание прочиталось как 127. **TOOL-ANDROID-BRIDGE-003:** на свежезагруженном эмуляторе `android init` падает до полной загрузки |
| `accessibility` | Нужный UI невозможно надёжно наблюдать | **AX-IOS-003.** Native Picker критичности не отдаёт label, value и ID — результат выбора подтверждается только через API. **AX-IOS-009 / AX-ANDROID-003:** содержимое code-block (тело ответа, cURL) недоступно в дереве |
| `oracle` | Неверная или недостаточная проверка постусловия | Ложных PASS за исследование — **0**. Но класс проявился как *недоказуемость*: без финального UI outline UI-проверки честно дают `INCONCLUSIVE`, а не PASS (проверено selftest). Alert несохранённых изменений живёт только во время run, поэтому его показ вынесен в `manualChecks` |
| `charter` | Задание двусмысленно или непроверяемо | Не встречалась: charter'ы формулировались с явной областью и риском. Но конструктивно предусмотрена — charter не может дать автоматический PASS, только `manualChecks` с ручным подтверждением |

## Как отличить `agent` от `sim-use` и `accessibility`

Частая путаница. Практическое правило из runbook:

- команда завершилась ошибкой или внутренним сбоем → `sim-use`;
- команда вернула `ok:true`, но постусловие не выполнено, **и** элемент в
  дереве был адресуем → `agent` (выбрал не то действие или не проверил);
- элемент **невозможно** надёжно наблюдать или адресовать без координат →
  `accessibility`;
- всё исправно, но приложение ведёт себя не по спецификации → `product`.

## Что даёт классификация

Из неё выводятся честные метрики. Например, `pass@1` 60% на Speecher выглядит
низким, но оба `FAIL` относятся к `product` — это измерение качества
приложения, а не способности инструмента. Без классификации такая цифра
читалась бы как провал подхода.
