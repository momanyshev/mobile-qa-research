# Selector guide

Как выбирать способ адресации элемента и почему. Правила выведены из 41 прогона
на трёх приложениях с принципиально разной разметкой: QA Lab Mobile (React
Native, разметка делалась намеренно хорошей), Speecher (SwiftUI, **ноль**
`accessibilityIdentifier`) и Element X (Compose, настоящие testID).

## Главный вывод

**Наличие testID определяет удобство, но не достижимость.** У Speecher
идентификаторов нет вовсе — и все пять сценариев прошли без единого
координатного тапа, потому что SwiftUI выводит доступные имена из видимого
текста. У QA Lab разметка отличная — но нативный wheel-picker всё равно
вынудил координаты.

Решает **тип контрола**, а не качество разметки. Обычные кнопки, поля и ячейки
списка адресуются надёжно почти всегда; платформенные «крутилки» и жесты — нет.

## Порядок выбора

1. **Стабильный ID** (`#issue-title-input`, `#login-continue`) — если есть.
   Единственный вариант, переживающий смену языка и правку текста.
2. **Точный label** (`--label "Создать дефект"`) — основной путь, когда ID нет.
3. **Уточнение по типу или области** (`--element-type Button`,
   `--frame maxY=…`) — когда label неоднозначен.
4. **Свежий alias** (`@12`) — только сразу после `ui`, в пределах одного
   экрана.
5. **Координаты** — последний путь. Допустимы без оговорок только для жестов
   (прокрутка, свайп), у которых целевого элемента нет по природе.

Метрика: доля успешных прогонов без координатных действий. Факт исследования —
100% на Speecher, 75% на Element X (единственное координатное действие за серию
— свайп прокрутки), 0% на QA Lab из-за wheel-picker.

## Три способа сломать селектор по label

Проверено на Speecher, все три встречались в одном приложении.

- **Локализация.** Смена языка переименовывает элементы: «Настройки» →
  «Settings». Сценарий, который сам меняет язык, обесценивает собственные
  селекторы прямо по ходу; в чужой локали даже пункт «Русский» становится
  «Russian». Вывод: сценарии смены языка строить только на ID либо переснимать
  дерево после каждого переключения.
- **Орфография.** Тап по «Тёмная иконка» не находит ничего, потому что в
  приложении написано «Темная», без «ё». Подпись брать **из свежего дерева**, а
  не из ожиданий или макета.
- **Коллизии.** Два «Закрыть», два «Создать дефект», два «Удалить» на одном
  экране (этап 3). Лечится `--element-type` или `--frame`, а по-хорошему —
  требованием к приложению дать уникальные имена.

## Обязательное правило: постусловие важнее селектора

`ok:true` от инструмента **не является** доказательством результата. Tap может
попасть в системную зону, в устаревший alias или в перекрытый overlay и всё
равно вернуть успех.

После каждого действия — свежий `ui` и проверка постусловия, а окончательный
verdict выставляет независимый oracle, а не факт выполнения команды.

## Платформенные особенности

**iOS.** Дерево содержит off-viewport элементы с реальными off-screen
координатами, поэтому `tap #id` по элементу вне экрана промахивается: сначала
прокрутить элемент в viewport, потом действовать. Wheel-picker не отдаёт
label/value/ID — надёжный приём не свайп (инерция перелетает), а **пошаговый тап
по строке, соседней с центром**: ровно один шаг за тап.

**Android.** Дерево равно viewport: элемента вне экрана «не существует», надо
прокрутить и переснять. Нижние кнопки могут попадать в системную навигационную
зону — помогает `--frame maxY=…` с `--element-type Button`. Системный overlay
(Gboard, «Try out your stylus») делает app-scoped `ui` пустым — диагностировать
через `adb exec-out screencap`.

## Что требовать от приложения

Список требований к тестопригодности, выведенный из blind spots, — раздел B и
E3 в [test-asset-register](../test-asset-register.md). Кратко: уникальные
идентификаторы у критических контролов, доступные имена у платформенных
picker'ов, связь значения счётчика с его подписью, стабильные роли.
