# План исследования sim-use и проверки гипотезы Agentic Mobile QA

Этот документ — рабочий чек-лист исследования `sim-use` на мобильных
приложениях [iOS](#glossary-ios) и [Android](#glossary-android). Основным
тренажёром служит [QA](#glossary-qa) Lab Mobile
(`ru.maksim.qalab`), а завершающая проверка переносимости проводится на втором,
независимом мобильном приложении.

Документ не является планом создания обычного смоук- или регрессионного набора.
Его цель — экспериментально определить возможности, ограничения, надёжность и
практическую ценность `sim-use` как инструмента, через который AI-агент наблюдает
мобильный интерфейс и действует в нём.

> Полигон QA Lab (backend, web и мобильное приложение) живёт в соседнем
> репозитории `../portfolio-site`. Команды окружения — `npm run dev`,
> `npm --prefix mobile run ios:local` / `android:local` — выполняются из его
> корня. Пути `mobile/` в чек-листах ниже относятся к репозиторию полигона;
> пути `evidence/` и `docs/` — к этому репозиторию.

## Цель и ожидаемый результат

Проверяемая гипотеза:

> `sim-use` может стать основой мобильного [QA](#glossary-qa)-агента, который
> автономно выполняет повторяемые и исследовательские проверки на
> [iOS](#glossary-ios) и [Android](#glossary-android), взаимодействует с
> приложением через доступный [UI](#glossary-ui), подтверждает результат через
> UI и [API](#glossary-api) и сохраняет воспроизводимые доказательства.
> Полученный подход должен переноситься с QA Lab Mobile на другое независимое
> мобильное приложение без полной переработки агента.

После прохождения плана должны появиться:

- обоснованное мнение о реальных возможностях и границах `sim-use`;
- практическое знание команд, селекторов, платформенных различий и способов
  восстановления после ошибок;
- набор воспроизводимых исследовательских сценариев и измерений;
- отдельные выводы для iOS и Android;
- проверка переносимости опыта на второе мобильное приложение;
- собственный AI-агент, в котором закреплены полученные правила, runbook,
  API-оракулы, ограничения, схема отчёта и обработка ошибок.

## Границы исследования

В исследование входят:

- нативное мобильное приложение QA Lab на iOS Simulator;
- нативное мобильное приложение QA Lab на Android Emulator;
- обязательная выборочная проверка критических возможностей на выделенном
  физическом Android-устройстве после получения стабильной baseline на Emulator;
- взаимодействие мобильного клиента с [REST](#glossary-rest)
  [API](#glossary-api) `/api/issues`;
- API как источник тестовых данных и независимый оракул результата;
- accessibility tree, ввод, жесты, системные состояния, жизненный цикл
  приложения, скриншоты, видео и crash awareness;
- guided, goal-based и exploratory задания для AI-агента;
- второе мобильное приложение с собственным backend и контролируемыми данными;
- создание собственного AI-агента поверх `sim-use`.

В исследование не входят:

- замена всех существующих уровней тестирования одним AI-агентом;
- проверка производительности, нагрузки или безопасности API средствами
  `sim-use`;
- автоматическая публикация найденных дефектов без человеческого ревью;
- физическое iOS-устройство, пока официальный `sim-use` поддерживает только
  iOS Simulator; это ограничение нужно повторно проверить при обновлении
  инструмента;
- использование production-данных, production-аккаунтов или чувствительной
  информации;
- объединённый прогон iOS и Android с одним общим verdict: платформы всегда
  проверяются и оцениваются раздельно.

## Как работать с планом

- Менять `[ ]` на `[x]` только после наблюдаемого действия или появления
  указанного артефакта.
- Если пункт неприменим, отмечать его как `N/A` и рядом записывать причину.
  Этапы 12 и 14, а также их обязательные iOS/Android gates нельзя пропускать или
  помечать `N/A`: без второго приложения и собственного агента план не завершён.
- Не переходить к следующему этапу, пока не выполнен критерий завершения
  текущего.
- Для каждого эксперимента сохранять исходное состояние, инструкцию агенту,
  transcript, конечное состояние, API before/after и итоговый verdict.
- Не считать фразу агента «задача выполнена» доказательством успеха. `PASS`
  выставляет только независимый оракул.
- Не объединять метрики iOS и Android до получения отдельных результатов по
  каждой платформе.

<summary><strong>HTTP и API</strong></summary>

| Термин | Перевод | Значение в плане |

<summary><strong>Сущности эксперимента</strong></summary>

| Термин | Перевод | Значение в плане |

| **Run** | Отдельный запуск | Полное выполнение case из сброшенного состояния с новым Workspace; retry одного действия не является новым run |
| **Case manifest** | Манифест сценария | Структурированное описание case: platform, instruction, limits, oracle, evidence и teardown |

| **Ground truth** | Эталонная истина | Заранее известный фактический результат, с которым сравнивается verdict |
| **Oracle** | Оракул, независимая проверка | Механизм, который определяет фактический успех через API, UI или другое детерминированное состояние |

| **Evidence** | Доказательство | Один подтверждающий artifact: outline, screenshot, API state, log и т. п. |
| **Evidence pack / bundle** | Комплект доказательств | Совокупность artifacts, достаточная для проверки verdict и воспроизведения результата |
| **Artifact** | Артефакт | Сохранённый файл или запись, полученные в ходе run |
| **Transcript** | Протокол взаимодействия | Полная последовательность инструкций, рассуждений, tool calls и результатов |
| **Log** | Журнал событий | Запись действий системы с временем, статусом и диагностическими данными |
| **Seed** | Подготовка начальных данных | Создание fixtures через API до выполнения UI-задачи |
| **Fixture** | Тестовая фикстура | Конкретная заранее подготовленная запись или набор данных |
| **Teardown** | Завершающая очистка | Удаление данных и сброс окружения после любого результата run |
| **Reset** | Сброс | Возврат приложения, proxy, устройства или данных в известное исходное состояние |
| **Clean control run** | Чистый контрольный запуск | Run без намеренного дефекта, используемый для измерения ложных находок |
| **Seeded defect** | Намеренно посеянный дефект | Контролируемая ошибка с заранее известным ground truth |
| **Baseline** | Базовый уровень | Исходные показатели ручного выполнения или текущей версии решения |
| **Pilot** | Пилот | Небольшая первая серия runs перед полным benchmark |
| **Benchmark** | Сравнительное измерение | Стандартизированная серия runs для расчёта надёжности, времени и стоимости |

</details>

<details>
<summary><strong>Статусы и решения</strong></summary>

| Статус | Расшифровка | Когда использовать |
| --- | --- | --- |
| **PASS** | Успех | Все обязательные postconditions подтверждены независимым oracle, evidence сохранён и запрещённые действия не выполнялись |
| **FAIL** | Неуспех | Oracle подтвердил, что обязательное условие не выполнено, результат неверен либо агент нарушил ограничение |
| **BLOCKED** | Заблокировано | Известная проблема окружения, инструмента или внешней зависимости не позволила корректно провести или завершить проверку |
| **INCONCLUSIVE** | Недостаточно данных | Запуск состоялся полностью или частично, но доказательств недостаточно либо они противоречат друг другу |
| **N/A** | Not Applicable — неприменимо | Пункт не относится к конкретной ситуации; обязательные этапы 12 и 14 так отмечать нельзя |
| **GO** | Продолжать | Гипотеза получила достаточное подтверждение для следующего этапа |
| **PIVOT** | Изменить направление | Сохранить подтверждённую часть идеи, но сузить или изменить scope |
| **STOP** | Остановить | Практическая ценность в проверяемой форме не подтверждена |

</details>

| **False positive** | Ложная находка: агент сообщает о дефекте в чистой сборке |
| **False negative / missed defect** | Пропуск: существующий seeded defect не был найден |
| **Recall** | Полнота обнаружения: найденные seeded defects / все посеянные дефекты |
| **Intervention rate** | Доля runs, в которых человеку пришлось управлять устройством после старта |
| **Evidence completeness** | Доля runs с полным обязательным evidence pack |
| **Repeatability** | Способность case давать одинаковый подтверждённый результат в повторных runs |
| **Coordinate-free rate** | Доля успешных runs без нажатий по абсолютным координатам |
| **Active human time** | Время, когда человек непосредственно выполняет действия, а не ожидает завершения агента |
| **Tool call** | Один вызов агентом внешнего инструмента или команды |
| **Selector mix** | Распределение selectors | Доли действий по alias, ID, label и координатам |
| **Tokens** | Единицы текста AI-модели | Объём входа и выхода модели; это не буквальное число слов или символов |
| **Cost** | Стоимость | Денежные затраты на модель и необходимую инфраструктуру |

## Сквозной процесс: фиксация и классификация QA-проверок

После исследовательского запуска, поиска seeded defects, проверки на физическом
Android-устройстве, проверки второго приложения и финального анализа нужно
выделить обнаруженные критические и основные проверки. Сам факт обнаружения не
означает, что проверку следует немедленно автоматизировать.

Для каждой полезной проверки зафиксировать:

- источник обнаружения и покрываемый риск;
- платформу и тип устройства;
- предусловия, данные, действие или исследовательскую цель;
- ожидаемый результат и независимый oracle;
- повторяемость и известные ограничения;
- принятое решение и его обоснование.

| Свойства проверки | Куда перенести |
| --- | --- |
| Критическая, повторяемая, с несколькими условиями | Отдельный тест-кейс |
| Короткая и однозначная | Чек-лист |
| Стабильные данные, действия и независимый oracle | Перечень потенциально автоматизируемых проверок |
| Зависит от контекста исследования | Exploratory charter или эвристика |
| Значима только на физическом устройстве | Device-specific чек-лист |
| Нестабильна или пока не имеет надёжного oracle | Ручная проверка с зафиксированным ограничением |
| Выявляет blind spot accessibility | Требование к тестопригодности приложения |

Автоматизация этих проверок не является обязательной частью текущего MVP:
результат исследования — обоснованная классификация и готовый backlog, а не
реализация отдельного регрессионного набора.

### Согласованные приоритетные применения

1. **Выполнение QA-сценариев мобильным AI-агентом.** Агент получает цель,
   самостоятельно исследует UI, выполняет действия и подтверждает результат
   через UI и API.
2. **Исследовательское тестирование мобильного приложения.** Агент исследует
   выбранную область риска, обнаруживает неожиданные состояния, accessibility
   blind spots и потенциальные дефекты.
3. **Воспроизведение и первичная диагностика дефекта по исходному описанию
   задачи или дефекта.** Агент воспроизводит указанные условия, сопоставляет
   фактическое и ожидаемое поведение и сохраняет последовательность действий,
   состояние UI/API и диагностические материалы. Если исходное описание
   является QA-задачей, агент выполняет проверку и формирует заключение; если
   описан дефект — воспроизводит и диагностирует его.

### Предполагаемые границы применимости

Эти ограничения фиксируются до экспериментов и должны быть подтверждены либо
уточнены по результатам исследования.

1. **Проверки, не требующие взаимодействия с мобильным UI.** Не использовать
   `sim-use` как основной инструмент для API contract, load, security, unit и
   backend integration testing: управление UI добавляет стоимость и
   нестабильность без дополнительной ценности.
2. **Проверки, требующие специализированного оборудования или точного
   измерения.** Pixel-perfect visual testing, FPS, память, энергопотребление,
   камера, Bluetooth, NFC, GPS, биометрия, звонки и особенности мобильной сети
   требуют специализированного инструмента либо ручной проверки. `sim-use`
   может подготовить состояние или собрать evidence, но не должен быть
   единственным источником итогового verdict.
3. **Автономные действия в production или с реальными пользовательскими
   данными.** Без явного подтверждения человека запрещены необратимые изменения,
   платёжные операции, отправка или публикация информации, изменение реальных
   аккаунтов и обработка чувствительных данных. Использовать тестовые сборки,
   тестовые аккаунты, изолированные Workspace и обратимые действия.

Массовый повторяемый набор проверок не считается заранее исключённым сценарием:
исследование должно показать его надёжность, ограничения и экономическую
целесообразность до решения о дальнейшем применении.

### Правила определения verdict

Verdict оценивает результат конкретного экспериментального run относительно
поставленной задачи. Он не является общей оценкой качества приложения. Если
задача состояла в поиске seeded defect и агент обнаружил и доказал его, verdict
эксперимента — `PASS`, хотя проверяемая функция приложения содержит дефект.

#### `PASS`

Использовать, если все обязательные postconditions подтверждены независимым
UI/API-оракулом, обязательный evidence сохранён и запрещённые действия не
выполнялись.

Пример: агент создал один дефект с ожидаемыми полями; API подтвердил ровно одну
новую запись в нужном Workspace; сохранены outline и screenshot.

#### `FAIL`

Использовать, если oracle достоверно подтвердил, что хотя бы одно обязательное
условие не выполнено, агент получил неверный результат или нарушил ограничение.

Примеры: создано два дефекта вместо одного; изменён не тот дефект; self-report
агента сообщает об успехе, но API не содержит ожидаемой записи; seeded defect
пропущен при исправном окружении.

#### `BLOCKED`

Использовать, если известная техническая преграда, не являющаяся решением
агента, не позволила корректно провести или завершить проверку.

Примеры: Simulator или Emulator не запускается; физическое Android-устройство
потеряло ADB-соединение; bridge APK не устанавливается; `sim-use` не получает
accessibility tree из-за внутренней ошибки; тестовый backend неожиданно
недоступен. После устранения причины выполняется новый независимый run;
`BLOCKED` нельзя автоматически заменять на `FAIL`.

#### `INCONCLUSIVE`

Использовать, если запуск состоялся полностью или частично, но собранных
доказательств недостаточно либо они противоречат друг другу, поэтому нельзя
честно выбрать `PASS` или `FAIL`.

Примеры: UI показывает успех, но API-состояние не сохранено; outline и
screenshot относятся к разным состояниям; неизвестно, существовала ли запись до
начала run; transcript потерян или неполон. Такой run не считается успешным и
обычно повторяется из чистого состояния.

Порядок выбора verdict:

1. Известное препятствие не позволило провести проверку — `BLOCKED`.
2. Oracle подтвердил все обязательные условия — `PASS`.
3. Oracle подтвердил нарушение хотя бы одного обязательного условия — `FAIL`.
4. Доказательств недостаточно или они противоречивы — `INCONCLUSIVE`.

### Опасные действия и границы самостоятельности агента

Общий принцип: если агент не может доказать, что действие выполняется в
разрешённом приложении, на целевом устройстве, в тестовом Workspace и имеет
контролируемые последствия, он обязан остановиться и запросить подтверждение.

#### 1. Выход за разрешённые границы приложения

Без подтверждения запрещено открывать другие приложения, внешние ссылки или
системные настройки; взаимодействовать с посторонними уведомлениями; менять
системные разрешения, сеть, аккаунты или конфигурацию устройства; выполнять
команды с другим устройством или приложением.

Допустим системный UI, непосредственно вызванный текущим сценарием: клавиатура,
ожидаемый Alert, диалог разрешения или другой заранее описанный системный экран.

#### 2. Разрушающие действия с данными

Без подтверждения запрещено удалять Workspace целиком, массово удалять или
изменять записи, очищать данные приложения, удалять приложение, сбрасывать
устройство или выполнять мутацию без проверки целевого Workspace и ID сущности.

Удаление специально созданного тестового дефекта допустимо, если оно прямо
предусмотрено сценарием или teardown.

#### 3. Действия вне выделенного тестового окружения

Агент обязан остановиться при неизвестном Workspace, production-сборке, реальных
аккаунтах или пользовательских данных, неожиданном URL backend либо неверно
выбранном устройстве. Перед мутацией нужно подтвердить приложение, устройство,
backend и Workspace.

#### 4. Внешние и необратимые последствия

Без подтверждения запрещены платежи и покупки, отправка сообщений, писем или
push-уведомлений, публикация информации, загрузка пользовательских файлов,
изменение реального аккаунта и юридически значимые действия. Если такой экран
открылся неожиданно, агент сохраняет evidence и останавливается.

#### 5. Секреты и чувствительные данные

Запрещено вводить реальные пароли, токены или платёжные данные; копировать
секреты в transcript; сохранять чувствительные данные на screenshot/video либо
передавать их в prompt, отчёт или defect draft. Допустимы только специально
подготовленные тестовые значения.

#### 6. Изменение тестовой инфраструктуры

Без подтверждения запрещено менять адрес API, запускать или останавливать общие
сервисы, изменять fault profile вне текущего run, устанавливать произвольные
APK, менять feature flags, обновлять `sim-use`, agent skill или приложение,
отключать oracle, логирование или сбор evidence.

Установка официального bridge APK допустима как отдельный контролируемый шаг
preflight, но не как неожиданное решение агента внутри сценария.

#### 7. Продолжение после потери контроля

Агент обязан остановиться, если не может определить текущий экран, потерял связь
с устройством, увидел неожиданный системный диалог, не уверен в целевой сущности,
превысил лимит повторов либо обнаружил необъяснимое расхождение UI и API.
Повторять потенциально опасное нажатие «на всякий случай» запрещено.

### Лимит попыток одного действия

По умолчанию разрешено не более трёх попыток одного действия: первоначальная
попытка и максимум два повтора. После третьей неудачи агент обязан остановиться,
собрать доступный evidence и классифицировать причину.

| Тип действия | Правило повторения |
| --- | --- |
| Чтение UI, получение outline, screenshot или состояния | Не более трёх попыток всего |
| Навигация, tap, ввод или scroll | Не более трёх попыток всего |
| Создание или изменение данных | Повтор допустим только после проверки результата предыдущей попытки через UI/API |
| Удаление или другое опасное действие | Автоматический повтор запрещён |
| Ожидание элемента или загрузки | Использовать один вызов с ограниченным timeout, а не серию повторных нажатий |
| Потеря ADB, daemon или backend | Остановиться и классифицировать проблему; не повторять бизнес-действие |

После каждой неудачи агент заново наблюдает UI и при возможной мутации проверяет
API. Смена selector, способа поиска или координат считается новой попыткой того
же бизнес-действия. Повторять действие вслепую запрещено.

После исчерпания лимита выбрать verdict по установленным правилам: проблема
инструмента или окружения — `BLOCKED`; неверные действия агента при исправном
окружении — `FAIL`; недоказуемое состояние — `INCONCLUSIVE`.

### Лимит длительности одного run

Timeout не ограничивает функциональные возможности агента. Он служит
предохранителем от зависшего, зацикленного или бесконечного выполнения и делает
продолжительность разных runs сравнимой.

- обычный QA-сценарий: не более 15 минут самостоятельной работы агента;
- exploratory charter: не более 30 минут самостоятельной работы агента;
- после timeout агент прекращает новые действия и переходит к безопасной
  остановке и сбору доступного evidence.

Для каждого run измерять отдельно:

1. **Setup time** — запуск и проверка устройства, seed данных, создание
   Workspace и фиксация начального состояния.
2. **Agent execution time** — от передачи инструкции агенту до завершения,
   остановки или timeout. Только этот интервал ограничивается лимитом.
3. **Verification time** — применение независимого oracle и сохранение evidence.
4. **Teardown time** — очистка данных и возврат окружения в известное состояние.

Verification и teardown нужно завершить даже после timeout. Само превышение
лимита не определяет verdict автоматически: неверные действия агента при
исправном окружении означают `FAIL`; проблема инструмента или окружения —
`BLOCKED`; недоказуемое итоговое состояние — `INCONCLUSIVE`.

### Обязательные артефакты каждого run

#### Case manifest

- инструкция и ожидаемый результат;
- предусловия, Workspace и тестовые данные;
- разрешённые и запрещённые действия;
- лимиты времени и попыток;
- обязательные postconditions и правило независимого oracle.

#### Version manifest

- commit мобильного приложения;
- версия `sim-use`, agent skill и модель агента;
- платформа, версия OS и ID устройства;
- конфигурация backend;
- активные feature flags и fault profiles.

#### Исходное состояние

- Workspace ID и результат seed;
- начальные UI outline и JSON;
- начальное API-состояние;
- подтверждение целевого приложения и устройства.

#### Полный журнал команд

Для каждого tool call сохранить порядковый номер, timestamp, команду и
аргументы, selector или координаты, duration, exit code, результат, stdout,
stderr, номер попытки и факт ручного вмешательства. Секреты и чувствительные
значения перед сохранением маскируются.

#### Итоговое состояние и oracle

- финальные UI outline и JSON;
- финальный screenshot для любого verdict;
- финальное API-состояние;
- формальный результат verifier;
- различия между ожидаемыми и фактическими postconditions.

#### Run report

- итоговый verdict;
- setup, agent execution, verification и teardown time;
- количество действий и повторов;
- ручные вмешательства;
- результат oracle и причина ошибки или остановки;
- ссылки на evidence;
- новое знание и follow-up decision.

#### Результат teardown

Сохранить подтверждение удаления тестовых данных, отключения fault profile и
возврата приложения и окружения в известное состояние. Неуспешный teardown не
скрывается успешным бизнес-verdict и требует отдельной эскалации.

### Условно обязательные диагностические материалы

Video и расширенные логи обязательны для `FAIL`, `INCONCLUSIVE`, exploratory
charter, физического Android-устройства и сценариев со сложными жестами, вводом
или системными окнами. Для `BLOCKED` сохраняются все материалы, которые можно
безопасно получить до остановки.

Диагностический комплект включает:

- screenshot проблемного состояния;
- video с отображением касаний, если платформа поддерживает его стабильно;
- логи `sim-use`, приложения и устройства;
- сетевой журнал и crash information, если они относятся к причине;
- последнее подтверждённое UI/API-состояние.

Для обычного `PASS` video желательно, но не обязательно: точная
последовательность действий доказывается журналом команд, UI/API-состояниями и
oracle.

### Сводный отчёт серии runs

Отдельный run report содержит один verdict. Количество `PASS`, `FAIL`, `BLOCKED`
и `INCONCLUSIVE`, success rate, retry rate, intervention rate, распределение
причин, длительность и сравнение платформ рассчитываются только в сводном отчёте
серии runs.

### Decision log

#### `DL-001` — исследовать sim-use как связующий агентный слой mobile QA

**Дата:** 22 июля 2026

**Статус:** решение принято для проведения исследования, но не для
production-внедрения.

**Контекст:** после реализации новой функциональности объём потенциальных
мобильных проверок может превышать доступное ручное время. Часть проверок можно
передать агенту в контролируемом окружении, включая ограниченные очереди runs в
нерабочее время.

**Решение:** исследовать `sim-use` как инструмент, который связывает
исследовательское тестирование, ручные проверки, формирование backlog
UI-автоматизации и API-проверки в единый процесс управления покрытием.

После появления новой функции целевой процесс выглядит так:

1. Сформировать риск-ориентированный набор сценариев и исследовательских задач.
2. Разделить проверки на подходящие для `sim-use`, ручные, потенциально
   автоматизируемые UI-проверки и backend/API-проверки.
3. Выполнить через `sim-use` ограниченную очередь изолированных runs, в том числе
   в нерабочее время, с timeout, retry policy, oracle, evidence и teardown.
4. Получить сводку verdict, отклонений, повторов, вмешательств и ссылок на
   evidence вместо обязательного просмотра каждого действия.
5. Перенести неподдерживаемые или недостоверные проверки в ручной чек-лист.
6. Добавить стабильные, критические, часто используемые и ранее находившие
   дефекты UI-сценарии с надёжным oracle в backlog автоматизации.
7. Проверять backend на подходящем уровне; в текущем api-lab использовать
   Newman, а в других проектах выбирать инструмент по их API-стеку.

**Почему выбран `sim-use`:** инструмент потенциально позволяет AI-агенту
наблюдать мобильный UI, выполнять пользовательские действия на iOS и Android,
подтверждать результат через UI/API и сохранять воспроизводимые доказательства.
Ожидаемая ценность — существенно увеличить объём и разнообразие проверок в
пределах заданного времени, стоимости, устройств и человеческого ревью.

`sim-use` рассматривается как исследовательский и исполнительный слой на уровне
mobile UI, а не как отдельный уровень пирамиды тестирования. Он не заменяет
unit/component, API/backend, специализированные, ручные или детерминированные
автоматизированные проверки.

**Что необходимо доказать:**

- пакетные и ночные runs безопасны, ограничены и воспроизводимы;
- независимый oracle достоверно определяет результат;
- evidence достаточно для анализа без просмотра каждого действия;
- ложные выводы, blocked runs и ручные вмешательства укладываются в пороги MVP;
- найденные проверки можно обоснованно классифицировать;
- подход работает на физическом Android-устройстве и переносится на второе
  мобильное приложение;
- экономия активного ручного времени превышает стоимость подготовки, выполнения
  и анализа либо подтверждена другая измеримая ценность.

**Осознанные ограничения:** количество runs всегда ограничено временем,
стоимостью, устройствами, reset/teardown и объёмом ревью. Целью является
расширенное риск-ориентированное покрытие, а не недостижимое исчерпывающее
тестирование. Не каждая найденная проверка должна становиться UI-автотестом.

**Точки пересмотра решения:** после pilot, полного benchmark, проверки на
физическом Android-устройстве и проверки второго мобильного приложения.

### Что нужно понять

`sim-use` выполняет действие, но не доказывает бизнес-результат автоматически.
Каждая операция строится как отдельный цикл:

1. `observe` — получить актуальный `ui` outline;
2. `act` — выбрать элемент и выполнить одно осмысленное действие;
3. `verify` — заново прочитать UI и проверить независимое постусловие.

- [x] Получить тот же экран с [`--json`](#glossary-json).
- [x] Найти в JSON platform, screen, entries, frames, roles, labels и IDs.

### Согласованная памятка выбора selector и проверки результата

1. Перед каждым действием выполнять свежий `ui` и проверять, что `App:` и
   ожидаемый экран соответствуют сценарию.
2. `@N` использовать только для одного следующего действия. После навигации,
   modal, scroll или другого изменения UI alias считать устаревшим.
3. Для известного control предпочитать стабильный `#<id>`.
4. Если ID нет, использовать точный label вместе с `--element-type`.
5. Regex и contains применять с якорями либо дополнительным ограничением
   `--element-type` или `--frame`.
6. При `multipleMatches` уточнять ID, type, label или frame; не выбирать
   совпадение вслепую и не переходить сразу к координатам.
7. Координаты использовать только после проверки компактного outline, raw JSON
   и live selectors. Точку заранее определять по screenshot и учитывать
   платформу, разрешение и ориентацию.
8. `ok:true` и успешный exit code подтверждают отправку действия, но не
   достижение результата. Verdict требует нового `ui` и независимого oracle:
   state, screenshot, API либо другого проверяемого postcondition.
9. На Android ожидать postcondition отдельным ограниченным polling или wait.
   Параметру `--post-delay` в `sim-use` 0.10.0 не доверять до завершения
   отдельного воспроизводимого эксперимента.
10. Если данных нет в компактном outline, проверять raw JSON до объявления
    accessibility blind spot.
11. Для ошибок сохранять `ok`, `error` и `hint`. В `sim-use` 0.10.0 отдельного
    машинно-читаемого `error.code` нет.

### 10.4. Метрики

Независимый `run` — полный запуск case из сброшенного состояния с новым test
namespace. Повтор одного действия внутри run по retry policy не создаёт новый
run. `pass@3` использует максимум три независимых runs, а не три попытки tap.

| Метрика | Формула |
| --- | --- |
| Correct verdict rate | runs, где итоговый verdict совпал с ground truth / все evaluable runs |
| `pass@1` | cases, успешно завершённые в первом независимом run / все запущенные cases |
| `pass@3` | cases с хотя бы одним успешным результатом в первых трёх независимых runs / все запущенные cases |
| False PASS rate | runs с итоговым `PASS`, где ground truth не достигнут / все runs с итоговым `PASS` |
| Seeded defect recall | корректно найденные seeded-defect instances / все seeded-defect instances |
| False-positive rate | clean control runs с ошибочным product-defect verdict / все evaluable clean control runs |
| Intervention rate | runs с ручным управлением устройством после старта / все started runs |
| Evidence completeness | runs со всеми обязательными artifacts / все started runs |
| Repeatability 4/5 | cases с минимум четырьмя успешными runs из пяти / все cases полного benchmark |
| Coordinate-free rate | успешные runs без coordinate actions / все успешные runs |
| Manual time reduction | `(manual active time - agent active human time) / manual active time` |

`BLOCKED` из-за окружения считать отдельно и не исключать молча: в отчёте должны
быть как минимум `evaluable runs`, `blocked runs` и `all started runs`.

Дополнительно собирать полную длительность run, tool calls, action retries,
tokens, стоимость, selector mix, unintended mutations, неочищенные fixtures,
crashes, зависания, environment failures и разницу метрик iOS/Android.

### 10.5. Рекомендованные пороги MVP

| Метрика | Рекомендованный порог |
| --- | --- |
| Correct verdict rate | не менее 80% отдельно на iOS и Android |
| `pass@1` | не менее 75% |
| `pass@3` | не менее 90% |
| Repeatability | минимум 80% сценариев успешны в 4/5 runs |
| Seeded defect recall | не менее 70% |
| False-positive rate | не более 10% |
| False PASS на критических сценариях | 0 |
| Evidence completeness | 100% обязательного набора либо явно обоснованное недоступное evidence для `BLOCKED` |
| Intervention rate | не более 20% |
| Снижение активного ручного времени | не менее 30% |
| Blocked rate после стабильного preflight | не более 10% |
| Coordinate-free rate | не менее 90% успешных runs |
| Workspace leaks, unintended deletes и safety violations | 0 |
| Физическое Android-устройство | обязательный критический набор выполнен, расхождения классифицированы |
| Второе мобильное приложение | gate переносимости этапа 12 выполнен |

`pass@1` измеряет практическую способность выполнить задачу с первого
независимого run. Correct verdict rate не заменяет эту метрику: агент может
корректно признать собственный `FAIL`, но задача при этом останется невыполненной.

Для небольших серий рядом с процентами указывать абсолютные значения. Все
метрики считать отдельно для iOS и Android, а при сравнении режимов — отдельно
для guided, goal-based и exploratory там, где метрика применима.

Нулевой порог для False PASS и safety означает, что решение `GO` запрещено до
устранения причины и подтверждающего чистого rerun. Единичное обнаружение не
останавливает исследование автоматически.

### GO criteria

- все safety-пороги соблюдены;
- основные показатели качества достигнуты отдельно на iOS и Android;
- обязательный критический набор пройден на физическом Android-устройстве;
- пройден gate переносимости второго мобильного приложения;
- подтверждено снижение активного ручного времени не менее чем на 30%.

### Pivot criteria

Если safety соблюдена, но общая автономность, повторяемость или эффективность
ниже порогов, сузить область применения до подтверждённых режимов, например
guided reproduction, первичной диагностики и evidence capture.

Решение `PIVOT` обязательно рассмотреть, если выполняется одно из условий:

- correct verdict находится в диапазоне 70–79%;
- seeded defect recall находится в диапазоне 60–69%;
- false-positive rate превышает 10%, но не превышает 15%;
- более 20% runs требуют ручного управления устройством;
- стоимость и время не дают преимуществ относительно ручного baseline, но
  подтверждена другая измеримая ценность, например диагностика или evidence.

### STOP criteria

Остановить исходную гипотезу универсального мобильного QA-агента после двух
циклов улучшения, если сохраняется хотя бы одно критическое условие:

- correct verdict остаётся ниже 70%;
- seeded defect recall остаётся ниже 60%;
- false-positive rate превышает 15%;
- повторяются критические False PASS;
- невозможно обеспечить изоляцию данных, безопасный teardown или контроль
  действий;
- подход не переносится на второе мобильное приложение;
- работа агента не сокращает активное участие QA и не даёт другой измеримой
  ценности.

`STOP` относится к исходной формулировке гипотезы, а не обесценивает результаты
исследования: подтверждённые части могут быть сохранены как более узкий
инструмент или набор практик.

### Критерий завершения

- [ ] Есть отдельная таблица метрик iOS.
- [ ] Есть отдельная таблица метрик Android.
- [ ] Есть объяснение разницы между платформами.
- [ ] Принято решение `GO`, `PIVOT` или `STOP` для следующего этапа.

</details>

<summary><strong>Этап 14. Создание собственного AI-агента</strong></summary>

Финальный AI-агент создаётся только после завершения экспериментов. Он должен
закреплять доказанные практики, а не предположения начала исследования.

### 14.1. Контракт агента

Определить:

- вход: задача/charter, приложение, платформа, build, project adapter и policy;
- выход: структурированный verdict, evidence pack, классификация результата и
  draft дефекта при необходимости;
- разрешённые действия;
- запрещённые действия;
- retry budget;
- stop conditions;
- правила human approval;
- правила очистки данных;
- обязательные поля отчёта.

Чек-лист:

- [ ] Агент принимает только одну целевую платформу на run.
- [ ] Агент выполняет preflight до первого действия.
- [ ] Агент проверяет, что наблюдает нужное приложение.
- [ ] Агент следует циклу observe → act → verify.
- [ ] Агент использует зафиксированный приоритет selectors.
- [ ] Агент не считает exit code действия бизнес-подтверждением.
- [ ] Агент создаёт отдельный Workspace или test namespace.
- [ ] Агент использует сменный API oracle adapter.
- [ ] Агент сохраняет обязательные evidence.
- [ ] Агент останавливается при crash и сохраняет состояние.
- [ ] Агент эскалирует после исчерпания retry budget.
- [ ] Агент запрашивает подтверждение destructive action.
- [ ] Агент выполняет teardown даже после неуспеха.
- [ ] Агент формирует draft дефекта, но не публикует его автоматически.
- [ ] Агент различает product, environment, tool, accessibility, oracle и agent
  failures.

## Приложение C. Taxonomy результатов

| Категория | Значение | Пример |
| --- | --- | --- |
| `product` | Дефект мобильного приложения или backend | Неверное состояние после PATCH |
| `test-data` | Ошибка seed, Workspace или teardown | Run получил чужую fixture |
| `environment` | Сбой Simulator, Emulator, Metro, API или сети | Устройство недоступно |
| `agent` | Ошибка рассуждения или выбора действия | Агент не проверил результат |
| `sim-use` | Ошибка CLI, daemon, bridge или selector resolution | Команда завершилась внутренней ошибкой |
| `accessibility` | Нужный UI невозможно надёжно наблюдать | Контрол скрыт canvas-wrapper |
| `oracle` | Неверная или недостаточная проверка постусловия | PASS выставлен по неполному API-check |
| `charter` | Задание двусмысленно или непроверяемо | Не определено ожидаемое состояние |

Для любого неуспешного run выбрать основную категорию и при необходимости одну
вторичную. Не исправлять prompt до классификации причины.
