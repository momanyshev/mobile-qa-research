# Этап 9. Каталог контролируемых дефектов и fault injection

Статус: **инфраструктура fault-профилей готова (9.2); каталоги сетевых и
прикладных дефектов рабочие; recall измерен на одном прикладном классе (9.3-R:
1/1 detected, 0/1 ложных), остальные классы — в 14.D.** Измерение требует
чистого контекста: знать посеянный дефект нельзя, иначе recall не измерить
честно.

## Механизмы внедрения

Два класса по способу внедрения:

- **Сетевые** — вносятся управляемым fault profile прокси `tools/proxy.mjs` без
  изменения приложения. Готовы и проверены.
- **Прикладные** — вносятся feature-флагами стенда с префиксом `seedDefect`
  (переменная окружения `QA_LAB_FF_SEED_DEFECT_*` при старте backend либо
  заголовок `X-Demo-Feature-Flags` на один запрос). Готовы три: поиск игнорирует
  описание, фильтр критичности игнорируется, разрешён любой переход статуса.
  Oracle к ним **иммунен** — `tools/lib/http.mjs` посылает все `seedDefect*` в
  положении `off`, поэтому эталон остаётся исправным, даже когда приложение под
  тестом сломано.

## Fault-профили прокси (9.2, готовы)

Управление: `node proxy.mjs enable <profile> [--params '<json>']` / `reset` /
`status`. Конфиг versioned (`schemaVersion`), читается работающим сервером на
каждый запрос, поэтому enable/reset действуют без перезапуска. `reset` возвращает
чистый pass-through и обязан вызываться в teardown каждого run, в том числе после
аварии. Все ответы, кроме намеренно искажённых, сохраняют контракт API.

| Профиль | Что делает | Проверено (curl) |
| --- | --- | --- |
| `passthrough` | без изменений | POST 201, GET сохраняются |
| `http-500` | 500 с контрактом ошибки | GET → 500 |
| `delay` | задержка `delayMs` | GET → 200 за ~1.6 с |
| `fail-first` | первый совпавший → `status`, далее успех | 503, затем 200 |
| `malformed-json` | портит хвост тела ответа | тело невалидный JSON (`…§`) |
| `disconnect` | обрыв соединения без ответа | curl exit 52 |
| `out-of-order` | ранние ответы задержаны сильнее поздних | req1 1.6 с, req2 0.09 с (инверсия) |
| `double-write` | дублирует мутацию (последовательно) | один POST → 2 записи |

Фильтр совпадения: `params.match.method` и `params.match.pathPrefix`
(по умолчанию все `/api/`). Request log помечает применённый профиль полем
`fault`. Evidence: `evidence/stage-9/fault-profiles-request-log.jsonl`.

## 9.3 Протокол поиска дефекта (→ этап 14)

Отложено до собственного агента с чистым контекстом. Готовый протокол:

1. не раскрывать агенту конкретный seeded defect;
2. дать одинаковый charter (из `stage-8-agent-modes.md`, CH-1…CH-3) чистой и
   дефектной сборке;
3. чистый контроль (без дефекта) для измерения false positives;
4. дефектная сборка отдельно на iOS и Android;
5. подтвердить наблюдение независимым oracle (`tools/`) или ручным ревью;
6. проверить качество шагов воспроизведения и достаточность evidence
   (transcript, outline, screenshot/video, API data);
7. подготовить draft дефекта, **не публиковать**;
8. классифицировать пропуск: agent / `sim-use` / accessibility / environment /
   oracle / некорректный charter;
9. классифицировать найденные проверки: тест-кейс / чек-лист / charter / ручная
   проверка / кандидат на автоматизацию.
