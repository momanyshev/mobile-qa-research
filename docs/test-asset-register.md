# Test asset register (сквозной процесс, этапы 3–13)

> **Сводный реестр этапа 13.2** — в конце документа, раздел «Единый реестр».
> Разделы A–E ниже — рабочая классификация по источникам обнаружения; сводный
> реестр собирает из них записи с ID, решением и обоснованием.


Классификация полезных проверок и наблюдений, найденных за этапы 3–7, по
категориям сквозного процесса плана. Это выполнение пункта 9 «Общего Definition
of Done» этапа 7, ранее не сделанного. Источники: карты accessibility (этап 3),
практика действий (этап 4), состояние/восстановление (этап 5), UI↔API и proxy
(этап 6), 24 сценарных run'а (этап 7), таблица «Системные наблюдения».

Правило: сам факт обнаружения не обязывает автоматизировать. Ниже — обоснованная
классификация и backlog, а не готовый регрессионный набор (это соответствует
scope MVP).

Категории (из плана):

- **TC** — отдельный тест-кейс (критическая, повторяемая, многоусловная);
- **CL** — чек-лист (короткая, однозначная);
- **AUTO** — кандидат на автоматизацию (стабильные данные/действия + независимый
  oracle);
- **CH** — exploratory charter/эвристика (зависит от контекста);
- **DEV** — device-specific чек-лист (значима только на физическом устройстве);
- **MAN** — ручная проверка с зафиксированным ограничением (нестабильна/нет
  надёжного oracle);
- **APP** — требование к тестопригодности приложения (blind spot accessibility).

### Обоснование отказов

- **R-20** — единственная запись со статусом «не проверять»: содержимое
  шифруется, независимого подтверждения не существует. Проверять по UI и
  называть это подтверждённым было бы самообманом.
- **R-12, R-15** — не автоматизируются осознанно: нет надёжного автоматического
  оракула (транзиентный alert; контекстное суждение charter'а). Перевод их в
  «авто» дал бы ложную уверенность.
- **R-11 (iOS)** — ограничение платформы, а не решение: снимется, если
  приложение даст доступный control со значением.
- **R-19** — отложено по недоступности устройства, а не по нецелесообразности;
  остаётся открытым долгом этапа 4.
