# Этап 8. Режимы работы AI-агента — дизайн и протокол

Статус: **дизайн готов, автономные прогоны отложены до этапа 14.**

Решение (24 июля 2026): этап 8 измеряет автономность агента при разном уровне
инструкций. Валидное измерение требует **чистого контекста** — агента без
накопленного знания приложения (id, координаты, обходы). Модель, ведшая
sim-use на этапах 3–7, таким контекстом не обладает, поэтому её «игра» в три
режима исказила бы сравнение. Поэтому здесь фиксируются готовые mode-промпты,
charter'ы, схема измерений и скелет сравнительной таблицы, а фактические прогоны
выполняет собственный агент этапа 14, для которого чистый контекст естественен.

Ниже — то, что агент этапа 14 берёт как есть.

## Общие правила прогонов (все режимы)

- отдельный run с новым Workspace [UUID] и полным evidence pack;
- инструкция агенту НЕ содержит команд `sim-use`, identifiers, alias или
  координат;
- независимый oracle (`tools/`) выставляет verdict; фраза агента «готово»
  доказательством не является;
- обязательные правила запуска — из раздела «Обязательные правила каждого
  запуска» плана;
- измеряется: setup / agent execution / verification / teardown time, tool
  calls, retries, ручные вмешательства, selector mix, coordinate-free (да/нет),
  oracle verdict.

## Три сценария для guided и goal-based (8.1, 8.2)

Выбраны так, чтобы покрыть разную сложность взаимодействия. Детерминированный
seed и oracle берутся из этапа 7.

### S1 — Создание дефекта (простая мутация; ср. 7.2)

- **Precondition:** пустой Workspace.
- **Guided prompt:** «Открой форму создания дефекта. Заполни название
  “Кнопка отправки остаётся неактивной” и описание
  “После заполнения всех полей кнопка не активируется”. Оставь критичность и
  статус по умолчанию. Сохрани дефект.»
- **Goal-based prompt:** «В приложении должен появиться ровно один дефект с
  названием “Кнопка отправки остаётся неактивной” и описанием
  “После заполнения всех полей кнопка не активируется”. Не создавай ничего
  лишнего.»
- **Oracle:** ровно 1 запись с ожидаемыми полями; inspector показывает
  `POST 201`; дублей POST нет (по request log proxy этапа 6).

### S2 — Переход статуса open → in_progress из карточки (Native Picker; ср. 7.6)

- **Precondition:** один посеянный дефект `severity=medium, status=open`.
- **Guided prompt:** «Найди дефект “Фильтр статуса сбрасывается”. Прямо в его
  карточке в списке измени статус с “Открыт” на “В работе”. Не открывай форму
  редактирования.»
- **Goal-based prompt:** «Дефект “Фильтр статуса сбрасывается” должен получить
  статус “В работе”. Ничего больше не меняй.»
- **Oracle:** `status=in_progress`; остальные поля не изменены; лишних записей
  нет. (Заметка: на iOS это wheel-picker — стресс на способ взаимодействия.)

### S3 — Удаление одного названного дефекта из нескольких (дизамбигуация +
destructive; ср. 7.8)

- **Precondition:** два посеянных дефекта: «Удалить этот» и «Оставить этот».
- **Guided prompt:** «В списке есть два дефекта. Удали только дефект с названием
  “Удалить этот”, подтверди удаление. Второй дефект не трогай.»
- **Goal-based prompt:** «В приложении должен остаться только дефект “Оставить
  этот”. Дефект “Удалить этот” должен быть удалён.»
- **Oracle:** удалённый ресурс → `404 NOT_FOUND`; список содержит только
  «Оставить этот» без изменений; `DELETE 204`. Destructive — требует явного
  подтверждения в UI по правилам этапа 0.

Каждый из S1–S3 выполняется в guided и в goal-based режиме, отдельно на iOS и
Android → 3 × 2 × 2 = 12 run'ов сравнения.

## Три exploratory charter (8.3)

Charter даёт область, риски и лимит времени, но НЕ маршрут. Лимит exploratory —
30 минут самостоятельной работы (этап 0).

### CH-1 — Workspace и изоляция данных

- **Область:** смена Workspace, персистентность, изоляция данных между
  пространствами.
- **Риски:** утечка записей между Workspace; неверный Workspace в запросах;
  потеря/подмена текущего пространства после relaunch.
- **Цель наблюдений:** подтвердить, что данные одного Workspace не видны в
  другом и переживают relaunch; зафиксировать любые расхождения UI и API.
- **Oracle/проверка:** независимые list-запросы по каждому Workspace;
  `expectWorkspaceIsolation`.

### CH-2 — Формы и несохранённое состояние

- **Область:** создание/редактирование, черновики, защита несохранённых
  изменений, валидация полей.
- **Риски:** потеря черновика без предупреждения; сохранение при отмене;
  ложная/пропущенная валидация; лишние мутации.
- **Цель наблюдений:** проверить поведение Alert несохранённых изменений,
  сохранность черновика при «Продолжить», отсутствие POST при отмене.
- **Oracle/проверка:** Workspace остаётся пустым при отмене; `expectCount`,
  `expectOnlyChanged`.

### CH-3 — Сетевые ошибки и восстановление

- **Область:** поведение при недоступном/сбойном backend и восстановление.
- **Риски:** незаметный silent-restart приложения агентом; мутации во время
  ошибки; отсутствие error-state; неверное восстановление.
- **Цель наблюдений:** наблюдать error-state, затем успешную загрузку через UI
  после восстановления backend; убедиться, что мутаций не было и приложение не
  перезапускалось скрытно.
- **Oracle/проверка:** `expectCount`/`expectFields` до и после; request log
  proxy; правило «PASS только по oracle».

Каждый charter выполняется отдельно на iOS и Android (6 exploratory-сессий) с
ручным ревью найденных наблюдений и evidence.

## 8.4 — Prompt и skill drift (протокол)

- сохранять точный prompt каждого run (в `runs.jsonl` поле `prompt`);
- сохранять revision agent skill (версия SKILL.md/`sim-use` из version manifest);
- повторить один сценарий (рекомендуется S2 — самый чувствительный к
  взаимодействию) с чистым контекстом агента;
- повторить тот же сценарий после изменения skill;
- критерий улучшения — рост **oracle pass**, а не только «лучше звучащий» ответ;
- зафиксировать конкретные правила prompt, которые реально изменили verdict
  (например: «перед tap по контролу у края экрана проверять его frame в
  viewport» — правило из этапа 7).

## Схема измерений (записывается на каждый run этапа 14)

| Поле | Смысл |
| --- | --- |
| `mode` | guided / goal-based / exploratory |
| `scenario` | S1–S3 или CH-1…CH-3 |
| `platform` | ios / android |
| `prompt` | точный текст инструкции агенту |
| `skillRevision` | версия agent skill |
| `setupSec` / `agentSec` / `verifySec` / `teardownSec` | тайминги |
| `toolCalls` | число вызовов sim-use/bash |
| `retries` | повторы одного действия |
| `interventions` | ручные вмешательства человека после старта |
| `selectorMix` | доли alias / id / label / координат |
| `coordinateFree` | обошёлся ли без абсолютных координат |
| `oracleVerdict` | PASS / FAIL / BLOCKED / INCONCLUSIVE |
| `notes` | наблюдения о поведении в этом режиме |
