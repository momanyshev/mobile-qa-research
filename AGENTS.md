# Правила работы в mobile-qa-research

## Что это за проект

Проверка гипотезы: `sim-use` может стать основой мобильного QA-агента,
который автономно выполняет проверки на iOS и Android и подтверждает
результат через независимый oracle. Полный контекст — в
`docs/testing-learning-plan.md`.

**Объект исследования — инструмент `sim-use`, платформенные
accessibility-деревья и окружение. Не приложение.** QA Lab Mobile из
`../portfolio-site` — только полигон. Это главное правило проекта: прошлые
сессии уже уходили в проверку функционала приложения, и эту работу
приходилось откатывать.

## Старт любой сессии

1. Открой `docs/testing-learning-plan.md`, найди «Карта прогресса» и строку
   «Текущий этап». Работай строго по чек-листу текущего этапа; не перескакивай
   и не возвращайся без запроса пользователя.
2. Перечитай разделы плана «Как работать с планом» и «Обязательные правила
   каждого запуска» — они обязательны для каждого эксперимента.
3. Галочки `[x]` ставятся только после наблюдаемого действия или появления
   указанного артефакта. Пользователь ведёт чек-листы лично — не отмечай
   пункты авансом.

## Правила фиксации результатов

- `PASS` выставляет только независимый UI/API-оракул, никогда — самооценка
  агента или «выглядит правильно».
- В план записываются только **системные наблюдения**: поведение `sim-use`,
  платформенных деревьев iOS/Android, окружения — знания, переносимые на любой
  проект (раздел «Системные наблюдения» плана).
- Дефекты приложения-полигона в план не попадают. Нашёл дефект — зафиксируй
  одной строкой вне плана (issue полигона или короткая заметка пользователю)
  и продолжай работу по этапу. Не исследуй и не чини его.
- Evidence сохраняй в `evidence/stage-N/<platform>/`; имена файлов — короткие
  kebab-case описания состояния (`status-filter.png`,
  `api-unavailable-error.png`).

## Окружение

Полигон запускается из `../portfolio-site` (подробности и команды — в
`README.md` этого репозитория, зафиксированные версии — в этапе 1 плана).
Ключевые правила:

- один Metro-процесс нельзя переиспользовать между платформами: API URL
  зашивается в bundle платформенной командой; всегда проверяй фактический URL
  в API-инспекторе приложения;
- для Android в свежей shell-сессии нужны явные `JAVA_HOME` и `ANDROID_HOME`;
- перед экспериментом создавай отдельный Workspace UUID; teardown обязателен
  при любом verdict;
- намеренный relaunch приложения сопровождай `sim-use app-state --reset`,
  чтобы не искажать crash awareness.

## Шаблон стартового промпта при смене модели

```text
Работаем в mobile-qa-research по docs/testing-learning-plan.md. Прочитай
AGENTS.md и найди в плане «Карта прогресса» и текущий этап — продолжай строго
по его чек-листу. Объект исследования — инструмент sim-use; приложение QA Lab
(../portfolio-site) — только полигон. Дефекты приложения не чинить и не
исследовать — фиксировать одной строкой вне плана. В план записывать только
системные наблюдения об инструменте и платформах. PASS — только через
независимый oracle. Evidence — в evidence/stage-N/<platform>/.
```

## Git

Коммиты — короткие, в повелительном наклонении, одна логическая единица на
коммит. Evidence версионируется вместе с изменениями плана, к которым он
относится.
